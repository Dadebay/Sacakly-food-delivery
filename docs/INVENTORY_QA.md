# Склад: правила, защита и проверка

Дата: 13 сентября 2026. Область: ингредиенты, рецептуры, склад по филиалам,
резерв заказа, отмена, ручные движения и уведомления внутри админки.
Источники поведения: `PROJECT_CONTEXT.md`, Prisma и `orders/order-policy.ts`.

## Принятое поведение

Заказ сразу получает `COOKING`. При создании ингредиенты списываются по рецептуре
в выбранном сервером филиале. Остаток показывает доступное количество после
резерва. Отмена, разрешённая существующей политикой, возвращает точный резерв
до фактической передачи курьеру. Назначение курьера ещё допускает возврат.
С `OUT_FOR_DELIVERY` возврата нет. Для клиента действует окно 15 минут и только
свой заказ; права администратора на отмену остаются прежними.

| Статус при отмене | Возврат ингредиентов |
| --- | --- |
| `COOKING` | Да |
| `READY` | Да |
| `ASSIGNED_TO_COURIER` | Да |
| `OUT_FOR_DELIVERY` | Нет |
| `DELIVERED` | Нет |
| `CASH_RETURNED`, `RECONCILED`, `CANCELLED` | Отмена запрещена |

## Bad cases — отказ и защита от повторов

| ID | Попытка / сбой | Проверяемый результат |
| --- | --- | --- |
| B01 | Чтение склада клиентом, курьером или бухгалтером | `403` на всех складских GET; интерфейс бухгалтера не запрашивает склад |
| B02 | Изменение склада любой ролью кроме `ADMIN`/`SUPER_ADMIN` | `403` для создания/правки ингредиента, рецептуры и остатков |
| B03 | Нет токена, поддельный токен, выключенный аккаунт, отозванная сессия | `401`, без изменения остатков |
| B04 | В JWT написан `SUPER_ADMIN`, в базе пользователь — клиент | Проверяется роль из базы; `403` |
| B05 | Подмена `actorId`, `orderId`, `quantityAfter`, даты движения в теле | `400`; клиент не задаёт автора или историю |
| B06 | Ноль, недопустимый знак, лишняя точность, слишком большое число, NaN/Infinity, null/объект/массив | `400`; остаток и движения не меняются |
| B07 | Некорректный UUID, неизвестный ингредиент/филиал | `400` или `404` |
| B08 | Списание больше доступного остатка | `409`, движения и успешный аудит отсутствуют; отказ записан отдельно |
| B09 | Недостаточно одного из ингредиентов нового заказа | Вся операция, включая другие ингредиенты, откатывается |
| B10 | Два заказа или несколько списаний спорят за последний остаток | Проходят только обеспеченные операции; остаток никогда не отрицателен |
| B11 | Один ключ ручной операции с другим количеством или причиной | `409`; старое движение не переписывается |
| B12 | Чужой заказ отменяет другой клиент | `403`, возврата нет; в отказе записан фактический автор |
| B13 | Клиент отменяет после 15 минут | `403`; граница ровно 15 минут разрешена, +1 мс запрещена в матрице политики |
| B14 | Повторная или одновременная двойная отмена | Один победитель версии; один возврат; второй запрос `409` |
| B15 | Отмена одновременно с получением курьером | Один победитель версии; склад соответствует итоговому статусу |
| B16 | Устаревшая версия, запрещённая роль/переход, изменение после передачи | Существующая матрица заказа отказывает без изменения резерва |
| B17 | Смена единицы ингредиента с рецептом, остатком или движениями при нулевом остатке | `409`, история остаётся в прежней единице |
| B18 | Пустой рецепт, повторяющиеся/неизвестные ингредиенты, нулевой выход | `400` |
| B19 | Пустое имя или цена за пределами Decimal(12,6) | `400` до обращения к записи в БД |
| B20 | Переполнение остатка | `409`; если переполняется возврат, отмена и возврат откатываются вместе |
| B21 | БД отказала при сохранении аудита успешного списания | `500` без внутренних подробностей; склад и движение откатываются, отказ журналируется |
| B22 | Некорректный UUID филиала или limit > 100 в уведомлениях | `400`; ответ ограничен и не содержит ключи повторов |
| B23 | Временная ошибка загрузки, недостаточный остаток из формы | UI показывает ошибку/повтор; введённые значения сохраняются |
| B24 | Ответ на уже выполненную операцию потерян | Повтор из той же формы использует тот же ключ, без второго списания |

## Что записывается в журнал

- `inventory.ingredient.created/updated`: автор, время, значения ингредиента до/после.
- `inventory.recipe.upserted`: товар, выход, активность, ID, количества и единицы всех ингредиентов до/после.
- `inventory.stock.adjusted`: филиал, ингредиент, движение, автор, тип, причина, ключ повтора, изменение и остатки до/после.
- `inventory.order.adjusted`: заказ, причина, точные движения и остатки до/после; `OrderTransition` и обычный аудит заказа сохраняются.
- `inventory.request.rejected`, `order.request.rejected`: фактический автор, если он уже проверен, роль из базы, шаблон маршрута, метод, статус, адрес соединения и время. Непроверенный JWT не становится автором.

Успешная операция и её аудит коммитятся вместе. Отказы записываются за пределами
откатившейся транзакции. Токены, заголовки, тела запросов и параметры URL в этот
журнал отказов не попадают. В API нет изменения/удаления истории. Отметка
«просмотрено» в UI не удаляет журнал и движения.

## Границы защиты

Это проверка критических известных сценариев, а не доказательство отсутствия
всех возможных атак. Администратор по своей роли может внести новую ручную
корректировку или изменить/выключить рецептуру; это сохраняется в аудите.
Ключ повтора не доказывает, что поставка физически была: новый ключ — новая
операция. Старые API-клиенты без ключа остаются совместимыми, каждый их запрос
считается отдельной операцией. Товар без активной рецептуры по принятому правилу
остаётся доступен к заказу без списания ингредиентов.

Для выявления физической недостачи нужна сверка фактических остатков с журналом.
Владелец БД технически может изменить саму БД: текущий журнал не является внешним
неизменяемым архивом. Если БД аудита недоступна, запись отказа гарантировать
невозможно; сервер пишет об этом безопасное сообщение. Успешное списание без
своего аудита не проходит.
