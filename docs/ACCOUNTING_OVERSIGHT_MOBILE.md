# Бухгалтерия: смены, месяц и контроль действий

Веб-интерфейс: `/accounting`. Все запросы ниже используют `/api/v1` и обычный
Bearer JWT. Новый просмотр доступен только активным `ACCOUNTANT` и
`SUPER_ADMIN`; бухгалтеру также нужна страница `ACCOUNTING` в матрице доступа.
Выдача этой страницы другой роли сама по себе не открывает новый журнал.
Бухгалтер получает просмотр, а не право редактировать или отменять заказы.
Подтверждение переданного денежного пакета сохраняется.

## Время и принадлежность данных

- Часовой пояс — `Asia/Ashgabat`, UTC+5. Начало включительно, конец исключительно.
- `fromDate` и `toDate` — календарные даты, обе включены; максимум 366 дней.
  Например, февраль 2025: `fromDate=2025-02-01&toDate=2025-02-28`.
- `shiftKey=2025-02-01:first|second` заменяет календарный диапазон. Сданный
  пакет хранит свои границы; дальнейшее изменение расписания их не переписывает.
- Заказы и спрос относятся к периоду **создания** заказа. Сумма еды:
  `total - deliveryFee`, уже после скидки. Отменённые заказы исключены из спроса.
- Деньги относятся к периоду **возврата денег** (`operatorTakenAt`). Это другая
  выборка: заказ может быть создан в дневную смену, а деньги вернуться ночью.
- Журнал и счётчики действий относятся к времени **действия**, в том числе
  когда изменили или отменили заказ предыдущей смены.

## API

| Запрос | Результат |
| --- | --- |
| `GET /accounting/settings` | Названия и границы смен |
| `GET /accounting/shifts?fromDate=...&toDate=...` | Все смены диапазона, суммы к сдаче, пакеты и их авторы |
| `GET /accounting/report?fromDate=...&toDate=...` | Возвращённые деньги, переданное/подтверждённое, остаток, дневной график, пакеты, популярные блюда |
| `GET /accounting/overview?shiftKey=...` | Количество заказов, отмены и причины, редактирования, спрос на блюда, районы и кухни |
| `GET /accounting/orders?shiftKey=...&basis=created&page=1&limit=25` | Заказы по времени создания |
| `GET /accounting/orders?shiftKey=...&basis=cashReturned&page=1&limit=25` | Деньги, возвращённые в смену; для сданного пакета — его зафиксированный состав |
| `GET /accounting/orders/:id` | Состав, клиент, адресные детали, суммы, подарки, оценка, денежная запись, этапы и авторы |
| `GET /accounting/orders/:id/audit?page=1&limit=25` | Вся история заказа, связанные чеки и денежный пакет независимо от выбранных дат |
| `GET /accounting/carryover?shiftKey=...&direction=in|out` | Незавершённые заказы на входе/выходе смены |
| `GET /accounting/audit?fromDate=...&toDate=...` | Общий журнал сохранённых действий по всем разделам |

Для `overview`, `orders`, `carryover` и `audit` вместо `shiftKey` можно передать
календарные даты. Это позволяет проверить и начало/конец целого месяца.
Постраничные ответы: `{items, total, page, limit}`; `page` начинается с 1,
`limit` по умолчанию 25, максимум 100. Не считать первую страницу полным отчётом.
Заказы поддерживают точный `number` и `status`; журнал — точные `actorId`,
`action`, `entityType`. Идентификаторы заказов — UUID.

`report.summary.declaredHandoffAmount` — заявленная сумма пакетов, чьи смены
начались в периоде. `handoffDiscrepancy` — заявлено минус ожидаемая сумма этих
пакетов: отрицательное значение означает недостачу. Детали отдельных
расхождений, комментарии и авторы остаются в `handoffs`. Это не комиссия за
систему и не доказательство фактического пересчёта купюр.

`overview.summary.cancelledOrders/cancellationRate` относятся к созданным в
периоде заказам и их текущему состоянию. `cancellationEvents` — количество
переходов в отмену именно в течение периода. `editEvents` — редактирования
содержимого заказа. Популярность — порции, а не деньги; показываются по 10
самых частых и редких заказанных позиций. Блюда с нулевым спросом не входят в
«редкие». Переименованные блюда могут образовать отдельные исторические строки.
Районы и кухни берутся из сохранённых названий заказа; неизвестный район
показывается отдельно, без угадывания по адресу.

## Передача незавершённых заказов

В переходящие входят `COOKING`, `READY`, `ASSIGNED_TO_COURIER`,
`OUT_FOR_DELIVERY`, `DELIVERED`: еда ещё готовится/доставляется либо деньги
ещё не вернули. `CASH_RETURNED`, `RECONCILED`, `CANCELLED` не переносятся.
Заказ, созданный точно на границе смен, относится к новой смене и не считается
входящим из предыдущей. Передача не создаёт второй заказ или начисление.

`statusAtBoundary` восстанавливается по переходам, `status` — состояние сейчас.
`snapshot` — сохранённый состав/адрес/суммы на границе. Поля верхнего уровня
заказа показывают текущие значения: не использовать их вместо `snapshot` для
исторического сравнения. Если старое изменение не содержало полного снимка,
`historicalSnapshotAvailable=false` и `snapshot=null`; интерфейс должен
показать это ограничение. Для незавершённого периода `isProvisional=true`,
`boundary` — время текущего среза; это ещё не окончательная передача.

## Аудит и ограничения истории

Создание, редактирование, упаковка, назначение/смена курьера, переход статуса
и отмена заказа сохраняют бизнес-снимки. Изменения каталога, филиалов,
промокодов, баннеров, контактов, сотрудников и расписания дополнены данными
до/после; существующие складские, тарифные и прочие доменные события доступны
в общем журнале. Успешное действие и его доменный аудит фиксируются одной
транзакцией. Отклонённые операционные запросы записываются отдельно после
отката, без тел запросов, заголовков и секретов. Отказ базы при записи
отклонённого запроса остаётся техническим ограничением.

`metadata.before/after` или `previous/current` содержат сравнение. Для событий
другого вида отображайте сохранённые поля. Старые отсутствующие снимки нельзя
восстановить задним числом. Автор имеет постоянный `id`, а имя и роль в ответе
соответствуют текущей учётной записи. Секретные ключи метаданных скрываются.
API не предоставляет редактирование или удаление журнала. Журнал фиксирует
бизнес-действия, а не нажатия и перемещение по меню; он помогает проверке, но
не заменяет физическую сверку денег/остатков и контроль доступа к самой БД.

Ошибки: `400` — неверные параметры, `401` — нет действующей сессии,
`403` — нет права, `404` — заказ отсутствует. Записи читаются из API,
не вычисляйте финансовую или статусную правду отдельно на мобильном клиенте.
Swagger и TypeScript-схема обновляются командой `npm run api:client`.

## Время приготовления

`preparationMinutes` принимает целое число от 0 до 1440, включая **520**.
Значение сохраняется в блюде и новых строках заказа. Короткое блюдо в общем
заказе получает задержку кухонного чека `maxPreparation - preparationMinutes`.
Готовка 520 минут не обрезается до прежнего максимума 240; старые снимки заказов
не переписываются при изменении каталога.


## Additive readability fields — 2026-09-27

Order detail adds `cook`, `participants: [{ actor, actions }]`, and
`actualCourierUnknown`. Participant actions come from saved order audits and
transitions (`transition:<OrderStatus>`); assignment alone does not establish
that a historical technical courier performed delivery. Settlement details add
nullable `operator` and `accountant` actor objects. Missing names/actors must
remain visibly unknown.

Audit entries add nullable `orderId`/`orderNumber` and `relatedActors`. Receipt
events resolve their order too; non-order or missing entities return null.
Use the resolved order number and names in the journal; keep entity UUIDs in
secondary technical details. Existing fields and readonly role gates remain.
