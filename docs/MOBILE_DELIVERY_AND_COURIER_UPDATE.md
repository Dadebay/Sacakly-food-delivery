# ТЗ для мобильного приложения: адрес, доставка и работа курьера

Сквозная матрица регрессии и ручного QA для видимости курьера после доставки
поддерживается в `docs/COURIER_MAP_AND_PRINTER_ROUTING_QA.md`.

Документ можно передать мобильному разработчику как список обязательных
изменений. Контракт уже доступен в production.

```text
API_BASE_URL=https://a7-tagam.com.tm/api/v1
MAP_TILE_URL=https://a7-tagam.com.tm/tile/{z}/{x}/{y}.png
Swagger=https://a7-tagam.com.tm/docs
```

## Критические правила

1. После выбора адреса пользователь **не должен второй раз выбирать район / этрап**.
2. Координаты маркера — единственный source of truth для адреса и доставки.
3. Стоимость доставки нельзя хранить в приложении как константу. Никаких
   захардкоженных `15 TMT` или «бесплатно от 150 TMT».
4. Актуальную стоимость нужно получать через `POST /delivery/quote` после
   выбора/изменения локации и после изменения суммы корзины.
5. Итоговые `deliveryFee`, `discount` и `total` из ответа создания заказа
   всегда важнее предварительного расчёта на клиенте.
6. Старые ответы поиска или расчёта нельзя применять к новой локации.
7. До забора заказа администратор может вернуть назначение
   `ASSIGNED_TO_COURIER → READY`. После нажатия курьером «Забрал» и перехода в
   `OUT_FOR_DELIVERY` возврат назад запрещён для всех ролей.

## 1. Что удалить из клиентской логики

- Обязательный dropdown «Район / этрап» после выбора официального адреса или
  маркера.
- Локальные таблицы районов, цен и порогов бесплатной доставки как источник
  расчёта.
- Расчёт доставки по тексту адреса на телефоне.
- Сохранение старой цены доставки после перемещения маркера.
- Ожидание нажатия кнопки «Найти» как единственный способ открыть подсказки.
- Предположение, что назначенный курьер или статус заказа больше не изменится.
- Прямые запросы мобильного приложения к Nominatim или OSRM.

`GET /delivery/config` можно использовать для справочного отображения доступных
зон, но не для обязательного повторного выбора района после адреса.

## 2. Поиск официального адреса

Endpoint требует access token пользователя с ролью `CUSTOMER`:

```http
GET /api/v1/geocoding/search?q=Kemine&limit=6
Authorization: Bearer <customer-access-token>
```

Ограничения:

- `q`: от 3 до 160 символов;
- `limit`: от 1 до 10;
- серверного ограничения частоты запросов нет;
- ответ содержит `items`, каждый элемент имеет `label`, `latitude`,
  `longitude`, `aliases`, `provider`.

Требуемое поведение поля:

1. При вводе менее трёх символов закрыть dropdown и не делать запрос.
2. После паузы ввода `350 ms` автоматически выполнить поиск.
3. Enter или кнопка поиска выполняют запрос сразу, не ожидая debounce.
4. При новом тексте отменить предыдущий HTTP-запрос либо пометить его
   устаревшим. Ответ для старого текста нельзя показывать.
5. После ответа сразу открыть dropdown под полем. В нём должны быть состояния:
   загрузка, результаты, ничего не найдено и ошибка.
6. Нажатие на результат сохраняет его координаты, перемещает маркер и запускает
   новый `POST /delivery/quote`.
7. При ошибке запроса показать понятное сообщение и разрешить ручной повтор.

Пример ответа:

```json
{
  "items": [
    {
      "label": "Kemine köçesi, Aşgabat şäheri, Türkmenistan",
      "latitude": 38.05567,
      "longitude": 58.20034,
      "aliases": ["Kemine köçesi"],
      "provider": "NOMINATIM"
    }
  ],
  "attribution": "© OpenStreetMap contributors"
}
```

## 3. Один source of truth для карты, адреса и тарифа

На клиенте должен быть один объект выбранной доставки, а не независимые поля
«адрес», «маркер» и «район»:

```text
DeliveryLocation
├── latitude
├── longitude
├── officialAddress
├── quoteState: idle | loading | success | error
└── quote
    ├── fee
    ├── price
    ├── freeDeliveryThreshold
    ├── matched
    ├── etrap
    └── welayat
```

Любое из этих действий меняет `latitude/longitude` и запускает одинаковый
процесс расчёта:

- выбор результата поиска;
- выбор сохранённого адреса;
- нажатие на карту;
- окончание перетаскивания маркера;
- получение текущей геолокации телефона.

Алгоритм после изменения координат:

1. Сразу очистить старые `quote`, `fee`, `etrap` и старую ошибку.
2. Показать загрузку расчёта доставки.
3. Вызвать `POST /delivery/quote` с координатами и текущим `subtotal`.
4. Если `addressLine != null`, заменить видимый официальный адрес этим
   значением. Это исправляет ситуацию, когда маркер уже перемещён, а в поле
   остался предыдущий адрес.
5. Показать `fee` из ответа.
6. Сохранить `etrap.id` только при `matched=true` и ненулевом `etrap`.

Отдельный `GET /geocoding/reverse` для этого сценария не нужен: quote уже
выполняет reverse geocoding и возвращает официальный `addressLine`.

## 4. Получение актуальной цены доставки

Публичный endpoint, token не требуется:

```http
POST /api/v1/delivery/quote
Content-Type: application/json

{
  "latitude": 38.05567,
  "longitude": 58.20034,
  "subtotal": 120
}
```

`subtotal` — текущая сумма товаров до доставки. Допустимое значение:
`0..1000000`, не более двух знаков после запятой.

Пример успешного ответа с найденным этрапом:

```json
{
  "addressLine": "Kemine köçesi, Aşgabat şäheri, Türkmenistan",
  "latitude": 38.05567,
  "longitude": 58.20034,
  "subtotal": 120,
  "fee": 15,
  "price": 15,
  "freeDeliveryThreshold": 150,
  "etrap": {
    "id": 123,
    "welayatId": 1,
    "nameEn": "Kopetdag",
    "nameRu": "Копетдагский этрап",
    "nameTk": "Köpetdag etraby",
    "queuePosition": 1,
    "price": 15,
    "freeDeliveryThreshold": 150,
    "isDeliveryEnabled": true,
    "updatedAt": "2026-08-21T00:00:00.000Z"
  },
  "welayat": {
    "id": 1,
    "nameEn": "Ashgabat",
    "nameRu": "Ашхабад",
    "nameTk": "Aşgabat",
    "sortOrder": 1
  },
  "matched": true
}
```

Важно различать поля:

- `price` — базовый тариф зоны;
- `fee` — фактическая доставка с учётом порога бесплатной доставки;
- в UI и в предварительном итоге показывать именно `fee`;
- `freeDeliveryThreshold=null` означает, что бесплатная доставка для этой зоны
  отключена.

### Логика `matched`

| Ответ quote | Что показать | Что отправить в заказе |
| --- | --- | --- |
| `matched=true`, `etrap!=null` | Адрес, найденную зону и `fee` | `deliveryEtrapId=etrap.id` |
| `matched=false`, `etrap=null` | Адрес и fallback `fee`, без требования выбрать район | Поле `deliveryEtrapId` не отправлять |
| Ошибка запроса | Не придумывать цену, показать повтор | Не подтверждать заказ, пока пользователь не увидит успешный quote |

`matched=false` — это валидный результат, а не ошибка. Backend уже применил
настроенный администратором fallback-тариф. Пользователя нельзя отправлять в
dropdown районов.

Quote нужно повторить:

- после выбора или перемещения локации;
- после добавления/удаления товара;
- после изменения количества или варианта товара;
- после обновления корзины с сервера.

При частом изменении корзины запрос можно debounce на `250–350 ms`. Новый
запрос отменяет или логически инвалидирует старый. Перемещение маркера
обрабатывается на `drag end`, а не на каждом пикселе движения.

## 5. Создание заказа покупателем

```http
POST /api/v1/orders
Authorization: Bearer <customer-access-token>
Content-Type: application/json
```

Новый inline-адрес с однозначно найденным этрапом:

```json
{
  "items": [
    {
      "productId": "00000000-0000-0000-0000-000000000001",
      "variantId": "00000000-0000-0000-0000-000000000002",
      "quantity": 2
    }
  ],
  "deliveryEtrapId": 123,
  "addressLabel": "Дом",
  "address": "Kemine köçesi, Aşgabat şäheri, Türkmenistan",
  "latitude": 38.05567,
  "longitude": 58.20034,
  "entrance": "2",
  "floor": "4",
  "apartment": "21",
  "customerNote": "Позвонить у подъезда",
  "promoCode": "WELCOME15"
}
```

Если quote вернул `matched=false`, тело остаётся таким же, но
`deliveryEtrapId` нужно **полностью убрать**. Не отправлять случайный район и не
сохранять район из предыдущей локации.

Для сохранённого адреса можно отправить `addressId`. Перед подтверждением всё
равно выполнить новый quote по координатам этого адреса и текущему subtotal:
сохранённый тариф мог быть изменён администратором.

После `201 Created` полностью заменить локальный черновик данными ответа.
Показывать пользователю серверные:

```text
subtotal
discount
deliveryFee
total
deliveryWelayatName
deliveryEtrapName
status
version
```

Клиент не отправляет `deliveryFee` или `total` в запросе. Backend сам проверяет
каталог, промокод, доставку, ближайший филиал и итоговую сумму.

## 6. Экран курьера и переходы статуса

Список заказов курьера:

```http
GET /api/v1/orders?statuses=ASSIGNED_TO_COURIER,OUT_FOR_DELIVERY,DELIVERED&page=1&limit=100
Authorization: Bearer <courier-access-token>
```

Backend уже ограничивает список назначениями текущего курьера. Ответ
пагинирован (`items`, `page`, `limit`, `total`, `pages`); если активных заказов
станет больше `limit`, нужно загрузить остальные страницы. После обновления
списка добавлять новые назначения, обновлять существующие и удалять те, которые
больше не назначены этому курьеру.

Переход выполняется одним endpoint:

```http
PATCH /api/v1/orders/{orderId}/transition
Authorization: Bearer <courier-access-token>
Content-Type: application/json

{
  "status": "OUT_FOR_DELIVERY",
  "version": 7
}
```

Кнопки по текущему статусу:

| Текущий статус | Кнопка | Отправить status |
| --- | --- | --- |
| `ASSIGNED_TO_COURIER` | Забрал заказ | `OUT_FOR_DELIVERY` |
| `OUT_FOR_DELIVERY` | Доставил / завершить доставку | `DELIVERED` |
| `DELIVERED` | Сдал наличные | `CASH_RETURNED` |

Только назначенный курьер может подтвердить получение и доставку. В каждый
запрос отправляется актуальный `version` из последнего ответа API.

После успешного PATCH нельзя вручную увеличивать version и менять только status.
Нужно целиком заменить локальный заказ объектом, который вернул сервер.

Обработка конфликтов:

- `409 Conflict`: заказ уже изменён; выполнить `GET /orders/{orderId}`, заменить
  локальные данные и только потом разрешить повтор действия;
- `403 Forbidden`: неправильный курьер или запрещённый переход; обновить список
  и показать сообщение;
- `401 Unauthorized`: выполнить штатное обновление token либо повторный вход;
- повторный tap по кнопке блокировать, пока запрос выполняется.

Администратор может:

- поменять назначенного курьера до начала доставки;
- вернуть заказ на один этап назад только до подтверждения забора курьером;
- отменить активный заказ до возврата наличных;
- до забора изменить товары, количество, адрес, координаты и сумму.

Поэтому после foreground, push-события, ошибки перехода и ручного refresh нужно
получать актуальный заказ с сервера. Если до забора администратор вернул
`ASSIGNED_TO_COURIER → READY`, заказ должен исчезнуть из списка курьера. После
успешного перехода в `OUT_FOR_DELIVERY` backend не разрешит администратору
вернуть заказ в `ASSIGNED_TO_COURIER`.

## 7. GPS и маршрут курьера

До выпуска отдельного мобильного клиента тот же production-контракт доступен
на `https://a7-tagam.com.tm/courier`. Курьер входит под собственным номером,
нажимает «Начать смену и показать себя на карте» и завершает передачу только
кнопкой конца смены. Роль `COURIER` на этом маршруте не получает доступ к
операционной админке. Это web fallback: при блокировке телефона браузер может
приостановить фоновые GPS-события, поэтому нативный клиент всё равно должен
реализовать правила ниже.

В течение всей смены курьера, включая время без активного заказа и после
`DELIVERED`, отправлять GPS примерно каждые `10–15` секунд:

```http
PUT /api/v1/tracking/me/location
Authorization: Bearer <courier-access-token>
Content-Type: application/json

{
  "latitude": 37.9601,
  "longitude": 58.3261,
  "accuracy": 12,
  "heading": 95,
  "speed": 8.5,
  "recordedAt": "2026-08-21T16:00:00.000Z"
}
```

Ограничения: `accuracy=0..5000`, `heading=0..360`, `speed=0..100`.
Ориентироваться на `nextUpdateInSeconds` из ответа. Завершение доставки не
должно останавливать GPS: диспетчерская карта покажет такого курьера как
`Свободен` и продолжит двигать его маркер. Только при завершении смены или
явном отключении геолокации:

```http
DELETE /api/v1/tracking/me/location
Authorization: Bearer <courier-access-token>
```

Маршрут и все назначенные остановки:

```http
GET /api/v1/orders/courier/route
Authorization: Bearer <courier-access-token>
```

Правила отрисовки:

- `stops` всегда показывать полностью;
- при `routingStatus=READY` рисовать `route.geometry` как GeoJSON LineString;
- пары в geometry идут в порядке `[longitude, latitude]`;
- `route.nextWaypoints` — только ближайшие 1–3 действия, а не полный список;
- при `routingStatus=UNAVAILABLE` сохранить маркеры и список адресов, даже если
  линия маршрута недоступна;
- при `NO_STOPS` показать пустое рабочее состояние;
- обновить маршрут после GPS, назначения и перехода статуса, но не позже
  `recalculateAfterSeconds`;
- не строить прямые линии между точками и не вызывать OSRM с телефона.

Подробный контракт карты и route response описан в
[`docs/MOBILE_MAP_AND_ROUTING.md`](./MOBILE_MAP_AND_ROUTING.md).

## 8. Отслеживание курьера покупателем

Для собственного заказа покупатель может получать текущую позицию назначенного
курьера:

```http
GET /api/v1/tracking/orders/{orderId}/courier-location
Authorization: Bearer <customer-access-token>
```

Не показывать позицию другого заказа и не кэшировать GPS как долгоживущие
данные. Если позиция отсутствует/устарела, показать соответствующее состояние,
а не старый маркер как текущий.

## 9. Минимальные тесты перед выпуском

### Покупатель

- Ввод трёх символов запускает autocomplete через 350 ms, результаты сразу
  открывают dropdown.
- Быстрый ввод не применяет ответ для старого поискового текста.
- Enter и кнопка запускают поиск сразу.
- Выбор результата перемещает маркер и вызывает quote.
- Перетаскивание маркера меняет видимый официальный адрес и цену.
- `matched=true`: в заказ уходит правильный `deliveryEtrapId`.
- `matched=false`: район не запрашивается, ID не уходит, показывается fallback
  `fee`.
- При достижении порога бесплатной доставки показывается `fee=0`, а не `price`.
- Изменение количества товара повторно вызывает quote.
- После создания заказа UI показывает серверные `deliveryFee` и `total`.
- Ошибка/устаревший quote не оставляет активной кнопку подтверждения с прошлой
  ценой.

### Курьер

- Назначенный заказ появляется без перезапуска приложения.
- «Забрал» переводит `ASSIGNED_TO_COURIER → OUT_FOR_DELIVERY`.
- «Доставил» переводит `OUT_FOR_DELIVERY → DELIVERED`.
- «Сдал наличные» переводит `DELIVERED → CASH_RETURNED`.
- Двойной tap не отправляет два transition-запроса.
- При `409` приложение перечитывает заказ и использует новый `version`.
- Смена курьера администратором удаляет заказ у прежнего курьера.
- Откат `ASSIGNED_TO_COURIER → READY` до забора удаляет заказ из работы
  курьера.
- После перехода в `OUT_FOR_DELIVERY` попытка admin rollback запрещена.
- `UNAVAILABLE` route не скрывает stops.
- GPS отправляется с timestamp устройства всю смену, включая паузы между
  заказами, и прекращается только после явного stop.

## 10. Критерии готовности

- Нет обязательного выбора района после выбора адреса.
- Нет локальных констант цены доставки.
- На экране до подтверждения показан успешный актуальный quote для текущих
  координат и subtotal.
- Адрес, маркер, etrap и fee обновляются одной транзакцией состояния и не могут
  относиться к разным локациям.
- Все суммы после создания заказа заменяются данными backend.
- Курьер использует versioned transition endpoint и умеет переживать
  pre-pickup rollback, reassignment и conflict; после pickup backward transition
  отсутствует.
- Маршрут, stops и GPS работают через NestJS API; карта использует общий raster
  endpoint A7-tagam.


## Дневные и ночные тарифы

Доставка поддерживает отдельные ночные цены и бесплатные пороги, настраиваемые
в админке. `price` в конфиге района остаётся дневной ценой. Для отображения
стоимости используйте серверный `fee` из `/delivery/quote` или нового
`/delivery/tariff-quote`, учитывайте срок котировки `validUntil` и показывайте
итог из ответа создания заказа. Полный контракт и поведение существующих
заказов: [NIGHT_DELIVERY_TARIFFS.md](NIGHT_DELIVERY_TARIFFS.md).
