# Saçakly Customer — техническое задание мобильного приложения

Статус: **спецификация для разработки, нового native релиза ещё нет**. Это приложение для покупателя; кафе и OWNER не управляют заказами через него. Общие правила авторизации, FCM и ошибок — в [README](README.md).

## Сценарий пользователя

1. Открыть каталог без входа, выбрать язык `tk/ru/en` и активное кафе. `GET /marketplace/cafes` возвращает кафе, у которых включён `ORDERING`.
2. Открыть меню выбранного кафе через `GET /catalog/categories?cafeId=<UUID>`; показывать только категории и товары этого кафе. При переходе в другое кафе очистить корзину после понятного предупреждения либо держать отдельную корзину для каждого кафе. На checkout всегда одна корзина и один `cafeId`.
3. Перед заказом войти по SMS: `POST /auth/otp/request {"phone":"+993..."}`, затем `POST /auth/otp/verify {"phone":"+993...","code":"..."}`. Экран кода показывает срок действия из `expiresInSeconds`; `devCode` допускается только в локальной разработке и не выводится в production UI.
4. Ввести адрес или выбрать сохранённый (`/users/me/addresses`), координаты/район, комментарий и количество. Запросить серверный расчёт `POST /marketplace/checkout/quote` с `cafeId`, `items: [{productId, quantity, variantId?}]` и, при наличии, `latitude + longitude` или `deliveryEtrapId`. Показывать `subtotal`, `discount`, `deliveryFee`, `total` из ответа. Расчёт может измениться до подтверждения.
5. Нажать «Заказать». `POST /marketplace/checkout/orders` с тем же `cafeId`, актуальными `items`, адресом/координатами либо `addressId` и новым UUID `idempotencyKey`. Повтор сетевого запроса использует **тот же ключ и то же тело**. Успех — номер, кафе, позиции, сумма и `paymentMethod: CASH`. Не создавать локальный «успешный заказ» до ответа API.
6. История/детали: `GET /orders` и `GET /orders/:id` для собственных заказов. `PATCH /orders/:id/cancel {"reason":"...","version":N}` — отмена только своего заказа в течение 15 минут после создания, если сервер разрешает текущий статус; 409 требует перечитать заказ. `POST /orders/:id/rating` после доставки, если сервер допускает.
7. Push для клиентского inbox: `GET /notifications/me`, `GET /notifications/me/unread-count`, `PATCH /notifications/me/:id/read`, `POST /notifications/me/read-all`. По push или возврату в приложение перечитать заказ. Клиент не выбирает курьера и не меняет его назначение.

## Договорённости об экранах

| Экран | Данные и действия |
| --- | --- |
| Главная | Список активных кафе, выбор языка, вход в профиль. |
| Кафе | Название, меню, позиции и цены, корзина только этого кафе. |
| Корзина/checkout | Адрес, контакт, комментарий, серверный quote, оплата наличными, подтверждение. |
| Мои заказы | Список, детали, статус, допустимая сервером отмена, оценка после доставки. |
| Профиль | Телефон, адреса, язык, уведомления, выход. |

Статусы заказа в API: `COOKING → READY → ASSIGNED_TO_COURIER → OUT_FOR_DELIVERY → DELIVERED`; затем внутренние `CASH_RETURNED` и `RECONCILED`. `CANCELLED` — отдельный конечный статус. Покупателю можно объединять внутренние статусы в понятные подписи, сохраняя исходное значение для логики. Статус заявки на доставку (`WAITING/OFFERED/CLAIMED/ASSIGNED/CANCELLED`) — другой enum и не заменяет статус заказа.

Если у кафе нет активного собственного курьера, сервер автоматически планирует внешнее предложение. Если еда готовится 60 минут, публикация происходит через 20 минут после заказа: правило `max(0, preparationMinutes − 40)`; приложение клиента не запускает собственный таймер назначения и не обещает точный ETA. Менеджер кафе может выбрать собственного курьера или внешнюю сеть до захвата предложения. После подтверждения упаковки зарезервированный курьер назначается заказу.

## Текущие границы и задачи API до выпуска

- Веб уже использует `GET /marketplace/cafes`, меню, OTP, quote и checkout. Мобильная команда может брать этот поток за пример, но должна использовать OpenAPI для DTO.
- `/orders` и `/orders/:id` возвращают заказ, однако ответ не содержит полноценного отдельного `cafeId`/кафе для каждого заказа. Для много-кафейной истории нужен явный снимок кафе в клиентском DTO, проверенный для старых и новых заказов.
- Публичное меню через старый `/catalog/categories` фильтруется по `cafeId`, но это ещё не отдельный подтверждённый tenant-safe мобильный контракт. Проверить активность `ORDERING` и изоляцию каталога перед выпуском.
- Текущий `GET /tracking/orders/:orderId/courier-location` — старый путь; полноценное клиентское отслеживание и tenant audit пока в roadmap. Не обещать живую карту до нового контракта и проверки разрешений.
- Превращение клиента в `COURIER` сегодня меняет глобальную роль; часть customer-only API может тогда отказать. Нужна отдельная проверка сценария одного человека в обоих приложениях и, вероятно, переработка политики ролей.
- Нет онлайн-оплаты, фискального чека, возвратов, обещанного времени доставки и production адреса. Текущие печатные чеки — внутренние документы кафе.

## Приёмка мобильной реализации

- Корзина кафе A никогда не создаёт заказ с товаром или филиалом кафе B; 403/404/409 показаны без утечки чужих данных.
- Двойное нажатие «Заказать» и повтор после сетевого таймаута создают не больше одного заказа с тем же idempotency key.
- Цена и скидка на экране подтверждения соответствуют последнему quote; итоговый ответ сервера имеет приоритет.
- После выхода refresh token и FCM token удалены/отозваны; чужой заказ недоступен; на `401` сессия восстанавливается или пользователь возвращается к входу.
- На iOS/Android и малых экранах доступны все действия, крупные шрифты и три языка; push не содержит чувствительных деталей заказа на заблокированном экране.
