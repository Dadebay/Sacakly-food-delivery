# Saçakly Courier — техническое задание мобильного приложения

Статус: **спецификация для разработки, полного tenant-safe рабочего API пока нет**. Это отдельное приложение для собственного курьера кафе и курьера платформенной сети. Общие правила входа, FCM и ошибок — в [README](README.md).

## Кто получает заказ

| Тип | Доступ | Назначение |
| --- | --- | --- |
| Собственный курьер кафе | OWNER выдаёт активное членство `COURIER` конкретного кафе. | Менеджер выбирает его в маршруте `OWN`; до готовности это резерв, после упаковки сервер назначает заказ. |
| Курьер внешней сети | Подаёт заявку, OWNER утверждает её; аккаунт активен и имеет роль `COURIER`. | Видит опубликованные `NETWORK` предложения всех кафе, первый успешный `claim` резервирует заказ. |

Заявка внешнего курьера: `POST /marketplace/courier-applications`, проверка `GET /marketplace/courier-applications/me`. Статусы `PENDING`, `APPROVED`, `REJECTED`. Только OWNER принимает решение; заявка сама по себе не даёт доступ к заказам. Собственному курьеру кафе внешняя заявка не нужна для назначения, но без `APPROVED` он не видит общую ленту предложений. Клиентский и курьерский аккаунты используют один OTP вход; дальнейшее разделение прав обеспечивает API.

## Поток внешнего заказа

1. Кафе получает заказ. Если нет активного собственного курьера, сервер сразу создаёт `NETWORK/WAITING`; менеджер может также вручную выбрать сеть. **Push не рассылается сразу**, если еда долго готовится.
2. Сервер вычисляет `offerAt = createdAt + max(0, maxPreparationMinutes − 40) минут` по снимку позиций заказа. Для 60 минут приготовления уведомление/предложение появляется примерно на 20-й минуте. Действие таймера серверное; при задержке фонового процесса UI читает фактическое состояние.
3. При `OFFERED` сервер создаёт долговечные FCM события для утверждённых курьеров. `GET /marketplace/delivery/courier/offers` возвращает до 100 предложений: `orderId`, `orderNumber`, `cafeName`, `offeredAt`, `estimatedReadyAt`. **Адрес, телефон и детали покупателя до захвата не выдаются.** Push может задержаться или не быть замечен, поэтому экран обновляет ленту через API.
4. Кнопка «Взять» вызывает `POST /marketplace/delivery/courier/offers/:orderId/claim`. Первый атомарный захват выигрывает. 409/404 означает, что предложение уже недоступно; убрать его из ленты и обновить список. Повтор тем же курьером для уже захваченного им заказа идемпотентен.
5. `CLAIMED` означает резерв на время готовки, **не старт поездки**. Кафе отмечает упаковку всех позиций. Тогда заказ становится `READY`, а резерв превращается в `ASSIGNED_TO_COURIER`; курьер получает обычный push о назначении. Если блюдо уже упаковано при захвате, назначение может произойти сразу.
6. Отмена заказа или смена маршрута до захвата закрывает предложение; push может прийти позже, поэтому нажатие всегда сверяется с API. Клиентское приложение не участвует в claim.

Существующие серверные статусы доставки: `WAITING → OFFERED → CLAIMED → ASSIGNED`, либо `CANCELLED`. Они не равны статусам самого заказа. Курьер **не может** сам менять маршрут `OWN/NETWORK`, назначать другого курьера или выдавать себе доступ к чужому кафе.

## Экранная модель

| Экран | Данные и действия |
| --- | --- |
| Вход/заявка | OTP, текущий статус внешней заявки и ожидание решения OWNER. |
| Предложения | Только для утверждённой сети: кафе, номер, ожидаемая готовность, «Взять», обновление списка. |
| Мои доставки | Отдельно «зарезервировано» и «назначено»; собственные и внешние заказы должны различаться по источнику. |
| Детали назначенного заказа | Пункт выдачи, адрес и контакт клиента, сумма наличных, действия «Забрал» и «Доставил» только после серверной проверки назначения. |
| Профиль | Язык, push, доступность смены **после появления серверной модели**, выход. |

Физический цикл после назначения должен следовать [order-policy.ts](../../apps/api/src/orders/order-policy.ts): `ASSIGNED_TO_COURIER → OUT_FOR_DELIVERY → DELIVERED → CASH_RETURNED`. Наличные оплачивает клиент при доставке; `CASH_RETURNED` относится к сдаче денег, а `RECONCILED` выполняет уполномоченный персонал. Курьер не может подтверждать получение денег кафе вместо его ответственного сотрудника. Версия заказа обязательна при изменении статуса; после 409 перечитать данные. Не показывать клиентский адрес на экране предложения, в push или аналитике до назначения.

## Уже существующие API и блокеры выпуска

- Работают: заявка/просмотр статуса, `GET /marketplace/delivery/courier/offers`, `POST .../claim`, `PUT /notifications/devices`; проверка прав выполняется сервером. Менеджер видит своих курьеров через `GET /marketplace/delivery/merchant/cafes/:cafeId/couriers` и выбирает `POST .../orders/:orderId/route {mode:"OWN", courierId, expectedOrderVersion}` или `{mode:"NETWORK", expectedOrderVersion}`. Это веб-функция менеджера, не вызов курьерского приложения.
- Старые `GET /orders`, `GET /orders/:id`, `GET /orders/courier/route`, `PATCH /orders/:id/transition {status, version}` фильтруют назначенного курьера, но до мобильного выпуска их надо проверить на новых marketplace заказах, ролях и tenant boundary. Для курьера в статусе `CLAIMED` до назначения сейчас нет отдельного безопасного API «мои резервы» с местом выдачи и без адреса клиента.
- `PUT /tracking/me/location`, `DELETE /tracking/me/location` и `GET /tracking/orders/:orderId/courier-location` — импортированные пути. Нужно проверить tenant и доступ к странице/роли, согласовать отдельную модель включения геолокации и политику хранения. Нельзя запускать фоновый GPS как условие работы MVP без этого решения и разрешения ОС.
- Нет серверной модели смены/`online`, отказа курьера от принятого заказа, таймера повторного предложения после отказа, отдельного API назначения для собственного курьера и tenant-safe информации о точке выдачи до назначения. Это задачи API, а не заглушки на клиенте. При проблеме с доставкой курьер связывается с диспетчером; переназначение выполняет уполномоченный серверный маршрут.
- Старый `AdminPage.COURIER_WORKSPACE` может ограничивать `/orders/*` и `/tracking/*`. Выдача прав на эту страницу не должна служить обходом tenant авторизации; до релиза нужны целевые тесты.

## Приёмка мобильной реализации

- Неутверждённый курьер не видит предложения и данные клиента. Курьер кафе без внешнего утверждения видит только собственные назначения после готовности.
- Два курьера одновременно нажимают «Взять»: только один получает `CLAIMED`; второй видит обновлённое состояние без чужих данных.
- Долгая готовка не вызывает ранний push; 60-минутный заказ становится доступен после 20 минут по серверному времени. Неудачный FCM не блокирует получение предложения через API.
- До назначения клиентский адрес не показывается ни в предложении, ни в уведомлении. После назначения курьер может менять только свой заказ и только по допустимому переходу с актуальной версией.
- На выходе останавливается разрешённая геолокация, устройство удаляется из push регистрации, refresh token отзывается.
