# Скидки, акции и баллы кафе

## Настройка

1. OWNER выбирает кафе в кабинете и включает **«Скидки и акции» (`MARKETING`)**
   и/или **«Баллы и подарки» (`LOYALTY`)**. Активация версионируется и аудируется.
2. Администратор этого кафе открывает **«Акции и баллы»**. Создаёт автоматическую
   акцию либо промокод: процент/сумма TMT, минимальная стоимость блюд, максимальная
   скидка, срок, общий лимит и лимит на покупателя. Даты в кабинете — время
   Ашхабада (UTC+05); API принимает ISO timestamps.
3. В **«Меню и филиалы»** задаёт баллы за порцию каждого блюда: от 0 до 1 000 000.
   Новое блюдо по умолчанию даёт 0 баллов. Настройки меню могут менять ADMIN и
   OPERATOR по существующим правам каталога; акции и подарки — только ADMIN.
4. Создаёт подарок с названием, описанием, стоимостью в баллах и остатком.
   Пустой остаток означает отсутствие лимита. Выключение скрывает предложение;
   удаление истории и ручное изменение кошелька не предусмотрены.
5. Покупатель видит автоматические акции на странице кафе. На checkout может
   ввести промокод и выбрать подарки. Сервер возвращает итоговый расчёт.
6. Кафе видит скидку и названия подарков в заказе. Перед готовностью сотрудник
   отдельно отмечает упаковку каждого блюда **и каждого подарка**. Подарки
   печатаются нулевыми денежными строками на основном внутреннем чеке.

## Правила расчёта

- Один заказ, промокод, подарок и кошелёк принадлежат одному кафе. Одинаковый
  текст промокода разрешён в разных кафе; программа кафе A не работает в B.
- Без кода сервер выбирает одну лучшую доступную автоматическую акцию. Явный
  промокод заменяет её. Скидки не складываются, доставка не дисконтируется,
  денежная скидка не превышает стоимость блюд.
- Общий и персональный лимит расходуются только успешным созданием заказа,
  не запросом quote. Отменённый заказ также расходует применение промокода:
  отмена не восстанавливает этот лимит. Это защищает ограниченные акции от
  многократного использования через отмены.
- При параллельном checkout строки акций кафе блокируются в стабильном порядке.
  Лимиты, заказ и увеличение счётчиков фиксируются одной транзакцией. Повтор
  одинакового запроса с тем же idempotency key возвращает исходный заказ.
- Quote не резервирует скидку/подарок: до создания могут измениться остаток,
  баланс, срок или лимит. При 400/403/409 нужно перечитать данные и пересчитать.
  Суммы из успешного ответа создания заказа являются окончательными.
- Баллы за порции фиксируются в заказе, не зависят от денежной скидки и
  начисляются один раз после `DELIVERED` (включая существующий административный
  путь завершения). Нельзя потратить ожидаемые баллы этого же заказа.
- Подарки добавляются только к заказу еды. API: до 10 разных подарков, до 10
  штук каждого; веб позволяет выбрать по одной штуке до 10 разных подарков.
  Баллы и остаток списываются атомарно при создании заказа. Параллельные запросы
  не позволяют дважды потратить баланс или последний подарок.
- Отмена возвращает потраченные баллы и ограниченный остаток подарка, отменяет
  уже начисленные за заказ баллы. Если ранее начисленные баллы уже потрачены,
  баланс может стать отрицательным; новые подарки тогда недоступны.
- Выключенный LOYALTY прекращает новое начисление и обмен. Обещанные баллы
  уже созданного заказа, возврат при отмене, баланс и история сохраняются.
  Выключенный MARKETING не изменяет скидки уже оформленных заказов.
- Баллы — обмен на подарки, без оплаты части заказа, денежных выплат, переводов
  между кафе или сгорания. История API содержит последние 100 записей.

## API

Все пути относительно `/api/v1`; DTO генерируются в `packages/api-contract`.

| Метод и путь | Кто и что |
| --- | --- |
| GET `/marketplace/cafes/:cafeId/rewards` | Публичные активные автоматические акции и доступные подарки опубликованного кафе. Ручные промокоды не раскрываются. |
| GET `/marketplace/cafes/:cafeId/loyalty/me` | Авторизованный пользователь: только собственный баланс и история выбранного кафе. |
| GET `/marketplace/merchant/cafes/:cafeId/rewards` | ADMIN кафе: все настройки, включая выключенные. |
| POST `/marketplace/merchant/cafes/:cafeId/rewards/promotions` | ADMIN + MARKETING: создать акцию/промокод. |
| PATCH `…/promotions/:id` | Полная форма настроек + `expectedVersion`; конфликт 409. |
| POST `/marketplace/merchant/cafes/:cafeId/rewards/gifts` | ADMIN + LOYALTY: создать подарок. |
| PATCH `…/gifts/:id` | Полная форма настроек + `expectedVersion`; конфликт 409. |
| POST `/marketplace/checkout/quote` и `/marketplace/checkout/orders` | Добавить `promoCode?` и `gifts?: [{giftId, quantity}]` к существующему телу. |

Ответ quote содержит `discount`, `promo`, `pointsBalance`, `loyaltyPointsEarned`,
`loyaltyPointsSpent`, `gifts` и денежные итоги. Заказ хранит `promotionLabel`
и снимки подарков. Не вычисляйте разрешения и списания на клиенте.

## Совместимость и выпуск

Миграция `20261006170000_cafe_rewards` добавляет `CafePromotion`,
`CafeLoyaltyWallet`, scope-поля и индексы, разрешает 0 баллов у блюда. Она
применяется поверх существующих данных без переноса старых балансов.
`User.pointsBalance`, старые подарки/ledger и прежние заказы с
`loyaltyCafeId = null` сохраняют общую legacy-программу. Новые marketplace
заказы всегда фиксируют свой `loyaltyCafeId`; CHECK не допускает другое кафе.
Старые `/loyalty/*` маршруты не показывают и не изменяют подарки нового кафе.

Модули у существующих кафе не включаются миграцией автоматически. OWNER
активирует их после настройки. Промокоды, нативные приложения и физическую
печать на production эта миграция не публикует. Общие ограничения выпуска
остаются в [ROADMAP](ROADMAP.md).
