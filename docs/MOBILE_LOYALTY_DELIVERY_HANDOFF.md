# Задание для разработчика клиентского мобильного приложения

**Статус:** API и админка реализованы в ветке `codex/map-delivery-zones` этого репозитория. Ветка отправляется в GitHub без развёртывания на сервере. Клиентское Android-приложение находится в отдельном репозитории; описанные ниже экраны и вызовы в нём ещё нужно реализовать.

**Цель:** показать баллы за блюда и подарки, дать клиенту добавить подарок к доставке еды, показывать актуальную стоимость доставки и часы приёма заказов. Мобильное приложение не управляет печатью чеков: после создания заказа API сам ставит задания в очередь.

## Уже готово на стороне API и админки

- В каталоге администратор задаёт время приготовления и баллы за одну единицу блюда; публичный каталог возвращает оба поля.
- В админке есть создание и редактирование подарков с фото, ценой в баллах, остатком и видимостью. API хранит баланс клиента и историю операций, списывает баллы и резервирует подарок при заказе еды, начисляет баллы за блюда при `DELIVERED` и возвращает списанное при допустимой отмене.
- Администратор настраивает часы приёма заказов и выбирает тариф по районам/улицам или километрам, с разными дневной и ночной ставками. API отдаёт открытость приёма, режим тарифа и официальную цену.
- В админке настроены копии главного чека, ручная маршрутизация выбранных блюд по принтерам, очередь с отсроченными кухонными заданиями и отмена ожидающего чека. Для заказа с манты 10 минут и шашлыком 30 минут задание на манты становится доступным через 20 минут. При удалении блюда из заказа ожидающее задание синхронизируется. Мобильному приложению эти операции не нужны.
- В админке показаны отдельно клиенты, успешно вошедшие через OTP, и аккаунты, созданные оператором без входа. Анонимных посетителей без учётной записи сервер сейчас не считает.

## Что мобильному разработчику нужно доделать

1. **Магазин подарков.** Добавить экран со списком из `GET /loyalty/gifts`: фото, название, описание, цена в баллах и доступность. Добавить состояния загрузки, пустого списка и ошибки с повтором запроса. Список можно открыть без входа, но при выборе подарка попросить войти. `imageUrl` — путь вида `/api/v1/media/<uuid>.webp`; загружать изображение с того же API origin, что и остальное медиа.
2. **Мои баллы.** Для вошедшего клиента показать `pointsBalance` и историю `entries` из `GET /loyalty/me`. Для каждой записи показать тип операции, число баллов со знаком и время. После создания, доставки или отмены заказа заново получать баланс; не вести отдельный локальный счётчик.
3. **Корзина с подарками.** Разрешить добавить подарок только при наличии еды. Отправлять массив `gifts` и в `POST /orders/quote`, и в `POST /orders`; не прибавлять баллы к цене в манатах. Перед подтверждением показать баланс, списание, будущие баллы за еду, подарки и итог из quote. Сохранить выбор подарков при сетевой ошибке или `409`, чтобы клиент мог скорректировать корзину.
4. **Каталог и заказ.** Показать `loyaltyPoints` за единицу блюда и `preparationMinutes` как время приготовления блюда. В деталях заказа показать снимок `gifts[]`, `loyaltyPointsEarned` и `loyaltyPointsSpent`. Если есть отдельный экран сбора заказа для персонала, в нём также должны быть видны подарки как отдельные позиции заказа.
5. **Доставка.** Взять режим из `GET /delivery/config`, стоимость по адресу из `POST /delivery/tariff-quote`, а окончательную сумму из `POST /orders/quote`. При смене координат, состава еды или наступлении `validUntil` перезапрашивать quote. Клиент не выбирает между тарифом по улицам и километрам и не считает километры или округление сам.
6. **Часы приёма.** Проверять `GET /ordering-hours` при открытии оформления и после возвращения приложения из фона. Если `isOpen: false`, показать часы и закрыть отправку заказа, сохранив корзину. Ошибку `409`, если приём закрылся до ответа на `POST /orders`, показать с возможностью повторить позже.
7. **Тесты мобильного приложения.** Проверить сценарии из раздела «Приёмочные проверки» ниже, включая повтор запроса с прежним `idempotencyKey`, отсутствие баллов до `DELIVERED`, отмену с возвратом баллов, границу день/ночь и исчезновение подарка между quote и созданием заказа.

Эти пункты — работа в **отдельном мобильном репозитории**. В этом репозитории готовы серверные правила, админские настройки и OpenAPI-контракт.

## Источник данных

Использовать существующий HTTP-клиент и авторизацию приложения. Все пути ниже относительно текущего API base URL с префиксом `/api/v1`. Контракт: [`apps/api/openapi.json`](../apps/api/openapi.json). Сервер определяет баллы, наличие подарков, стоимость доставки, часы работы и окончательную сумму. Мобильное приложение показывает ответы сервера и не повторяет эти расчёты локально.

| Запрос | Авторизация | Для чего |
| --- | --- | --- |
| `GET /catalog/products` | Нет | Каталог; у блюда есть `loyaltyPoints` за **одну штуку** и `preparationMinutes`. |
| `GET /loyalty/gifts` | Нет | Доступные подарки; возвращается массив активных подарков с остатком больше нуля либо без ограничения остатка. |
| `GET /loyalty/me` | Токен клиента | Текущий баланс `pointsBalance` и последние операции `entries`. |
| `GET /ordering-hours` | Нет | `isOpen`, `enabled`, `opensAt`, `closesAt`, `timezone`, `serverTime`. |
| `GET /delivery/config` | Нет | Выбранный администратором способ расчёта: `distancePricingEnabled`; дневная и ночная ставки. |
| `POST /delivery/tariff-quote` | Нет | Тариф по текущим координатам и сумме блюд; возвращает `pricingMode`, `fee`, `distanceMeters`, `tariff`, `validUntil`. |
| `POST /orders/quote` | Токен клиента | Окончательная предварительная сумма заказа, список подарков, `loyaltyPointsEarned`, `loyaltyPointsSpent`, `pointsBalance`. |
| `POST /orders` | Токен клиента | Создание заказа с едой и необязательными подарками. |
| `GET /orders/:id` | Токен владельца | Сохранённые позиции, подарки, баллы и статус заказа. |

`GET /delivery/quote` также доступен, когда экрану нужен определённый по карте адрес вместе с тарифом. Для итоговой суммы корзины всё равно использовать `POST /orders/quote`.

## Что показать в приложении

### Каталог и карточка блюда

- Показывать «+N баллов после доставки» из `product.loyaltyPoints`. Это значение за одну единицу; в корзине использовать `quote.items[].loyaltyPoints` — сервер уже умножил его на количество.
- `preparationMinutes` можно показывать как время приготовления конкретного блюда. Не превращать его в обещанное время доставки или готовности всего заказа: такого ETA API не возвращает.
- После изменения блюда, варианта или количества снова запрашивать `POST /orders/quote`; цены и баллы из старой карточки могут устареть.

### Баланс и магазин подарков

- Добавить экран/раздел «Мои баллы» для вошедшего клиента: `GET /loyalty/me`. Операции имеют `kind`: `EARN`, `REDEEM`, `REFUND`, `REVERSE_EARN`; `points` содержит число со знаком. Показывать серверный `pointsBalance`, не суммировать историю самостоятельно.
- Добавить магазин подарков из `GET /loyalty/gifts`: `name`, `description`, `imageUrl`, `pointsCost`, `stock`. `stock: null` означает отсутствие лимита. Гость может просматривать подарки, но для выбора и заказа нужен вход в свой аккаунт.
- Подарок можно выбрать **только в корзине с едой**. Отдельной оплаты или отдельного заказа подарка нет. Не прибавлять `pointsCost` к сумме в манатах.
- При выборе подарка отправлять его `giftId` и `quantity` в `POST /orders/quote`, затем в `POST /orders`. Допустимо до 10 разных подарков, количество каждого — от 1 до 10. Кнопку подтверждения не активировать без хотя бы одного блюда.
- Показывать из ответа quote: `pointsBalance`, `loyaltyPointsSpent`, `loyaltyPointsEarned`, `gifts[]`, `total`. Баллы за текущие блюда начислятся **после статуса `DELIVERED`**; ими нельзя оплачивать подарок в этом же заказе, если до заказа баланса недостаточно.
- После успешного заказа, доставки или отмены обновлять баланс и каталог подарков. При создании заказа баллы за подарок списываются и остаток резервируется; при допустимой отмене они возвращаются. Отмена после начисления также может списать ранее заработанные баллы; баланс в редком случае бывает отрицательным — отображать значение API как есть.

### Доставка и часы работы

- Администратор выбирает один режим тарифа для всех клиентов. В `GET /delivery/config` поле `distancePricingEnabled: true` означает расчёт по километрам; `false` — действующий расчёт по районам/улицам. Это **не переключатель для клиента**.
- Для цены по километрам передавать координаты выбранного адреса (`latitude`, `longitude`). API выбирает ближайший активный филиал и считает прямое расстояние по формуле Хаверсина. OSRM для цены не используется. Минимум — 15 TMT, округление выполняет сервер (например, 16 → 15, 17 → 20). Ночной тариф и его границы тоже определяет сервер.
- Для предварительного показа доставки вызывать `POST /delivery/tariff-quote` с `subtotal`, `latitude`, `longitude` (в режиме районов можно также передать `deliveryEtrapId`). Показывать `fee`; `pricingMode` и `tariff` можно использовать для подписи. Если `validUntil` не `null`, после этого времени запрашивать цену заново. При изменении адреса или суммы блюд тоже запрашивать заново.
- На итоговом экране использовать `deliveryFee` и `total` из `POST /orders/quote`. Перед отправкой заказа повторить quote. При `POST /orders` сервер ещё раз пересчитает цену; ответ созданного заказа является окончательным. Не применять на телефоне собственную формулу, бесплатную доставку или округление.
- Получать `GET /ordering-hours` при входе в корзину/оформление и при возвращении приложения из фона. Если `isOpen: false`, показывать `opensAt`–`closesAt` с `timezone` и закрыть кнопку создания заказа; каталог и корзина остаются доступны. Если `enabled: false`, заказы принимаются всегда. Переход через полночь уже обработан сервером — ориентироваться на `isOpen`, а не на часы телефона. При смене времени сервер вернёт конфликт на создание заказа, даже если экран ещё показывал «открыто».

## Последовательность оформления

1. Клиент выбирает блюда, количество, адрес и, при желании, подарки. Для заказа нужен собственный вход клиента.
2. Приложение загружает часы работы, доступные подарки и баланс. По выбранному адресу и корзине получает актуальный `POST /orders/quote`.
3. Экран подтверждения показывает блюда, баллы после доставки, списываемые баллы, подарки, стоимость доставки и `total` из quote. При изменениях перезапрашивает quote.
4. Один раз генерирует UUID `idempotencyKey` для этой попытки заказа. Отправляет `POST /orders` с **тем же составом**. При сетевом обрыве повторяет тот же запрос с тем же ключом; при осознанном изменении корзины создаёт новый ключ.
5. После `201` показывает заказ и фактический `total` из ответа сервера, обновляет `GET /loyalty/me` и `GET /loyalty/gifts`. Для последующего просмотра использует `GET /orders/:id`. Между quote и созданием администратор может изменить тариф: текущий API пересчитает сумму при создании и не гарантирует отдельный `409` для такого изменения. Если продукту нужно обязательное повторное подтверждение новой суммы **до** создания заказа, потребуется расширить API-контракт.

Пример quote (UUID заменить реальными значениями):

```json
POST /api/v1/orders/quote
{
  "items": [{ "productId": "11111111-1111-4111-8111-111111111111", "quantity": 2 }],
  "gifts": [{ "giftId": "22222222-2222-4222-8222-222222222222", "quantity": 1 }],
  "latitude": 37.9601,
  "longitude": 58.3261
}
```

Пример создания того же заказа с уже сохранённым адресом:

```json
POST /api/v1/orders
{
  "idempotencyKey": "33333333-3333-4333-8333-333333333333",
  "addressId": "44444444-4444-4444-8444-444444444444",
  "items": [{ "productId": "11111111-1111-4111-8111-111111111111", "quantity": 2 }],
  "gifts": [{ "giftId": "22222222-2222-4222-8222-222222222222", "quantity": 1 }]
}
```

Создание заказа допускает и новый адрес через `address`, `latitude`, `longitude` вместо `addressId`. При использовании варианта блюда передавать `variantId` в строке `items`. В режиме расчёта по километрам у выбранного адреса обязательно должны быть координаты.

Временно для старых версий приложения `POST /orders` принимает `latitude: null` и `longitude: null` как отсутствие полей: координаты берутся из выбранного или активного сохранённого адреса. Это работает и для тарифа по улицам, и для тарифа по километрам. Новый клиент должен опускать эти поля при передаче `addressId`; новый адрес по-прежнему требует обе корректные координаты. Переключение обратно на улицы делается в админке через `distancePricingEnabled: false`, без отката backend; реальные координаты остаются допустимыми в обоих режимах.

## Ступени цены за километр

`GET /delivery/config`, `POST /delivery/tariff-quote` и `POST /delivery/quote`
дополнительно возвращают `distancePriceTiers`: массив правил с полями
`afterKilometers`, `dayPricePerKilometer`, `nightPricePerKilometer`.
Например, при начальной ставке 5 TMT/км правило «после 5 км — 4 TMT/км»
означает: первые 5 км по 5, только оставшееся расстояние по 4.
Для 6 км получается 29 TMT до общего округления и 30 TMT к оплате.
`pricePerKilometer` в quote остаётся начальной ставкой. Не умножать её на всю
дистанцию: показывать `fee` из delivery quote и `deliveryFee`/`total` из заказа.
Минимум 15 TMT и округление применяются сервером один раз к общей сумме.
Пустой массив означает одну ставку на всё расстояние. В режиме `AREA` quote
возвращает пустой массив, даже если в конфигурации сохранены ступени.
Отсутствие нового поля на старом сервере не должно ломать мобильный клиент.

## Ошибки и обновление данных

- `401`: попросить войти снова через существующий поток авторизации. Не отправлять подарок через служебный/телефонный заказ оператора.
- `400`: показать ошибку валидации; в частности, координаты должны идти парой, подарок должен быть доступен, количество должно быть допустимым.
- `409` при нехватке баллов, изменении остатка подарка, закрытых часах приёма заказов или иных конфликтах: не создавать локальный «успешный» заказ. Обновить баланс, подарки, часы и quote, затем показать клиенту новое состояние для повторного подтверждения.
- Таймаут после `POST /orders`: не создавать новый `idempotencyKey`, пока неизвестен исход. Повторить идентичное тело с тем же ключом.
- Ответ заказа и детализация `gifts[]` являются снимком на момент покупки. Если подарок затем скрыт или его цена изменилась, история заказа должна показывать сохранённые `name`, `imageUrl`, `pointsCost`, `quantity`, `totalPoints`.

## Приёмочные проверки мобильного приложения

- Блюдо с 3 баллами за единицу и количеством 2: каталог показывает «+3», quote и заказ показывают 6; баланс увеличивается только после `DELIVERED`.
- Подарок нельзя заказать без еды; недостаток баллов, исчезнувший подарок и закончившийся остаток не приводят к успешному заказу. При отмене баллы и ограниченный остаток восстанавливаются.
- При `distancePricingEnabled` приложение отправляет координаты, показывает стоимость от сервера и не предлагает клиенту выбирать районный тариф. При обратном переключении администратора экран принимает режим `AREA` без обновления приложения.
- Смена адреса, количества блюд и границы день/ночь обновляет quote; приложение не вычисляет цену 16 → 15 / 17 → 20 самостоятельно.
- При `isOpen: false` заказ недоступен; если время закрылось между просмотром и нажатием, `409` отображается понятно и корзина сохраняется.
- Повтор идентичного `POST /orders` после таймаута с прежним `idempotencyKey` не создаёт второй заказ.
- В истории заказа видны подарки и начисленные/списанные баллы. Чековый аппарат и его расписание не требуют вызовов из мобильного приложения.

## Граница выпуска

Мобильную реализацию проверять против версии API с этими полями после её публикации. Push ветки `codex/map-delivery-zones` **не обновляет production API**: деплой запускается только из `main`, а он здесь не выполняется. До совместного выпуска мобильное приложение должно сохранять совместимость с текущим сервером и не считать новые поля обязательными в ответах старой версии. Для обновления приложения использовать существующий механизм релиза Android; отдельной версии программы печати для этих функций не требуется.
